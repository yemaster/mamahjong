# 架构设计

状态：草案  
最后更新：2026-07-29

## 目标

- 首期支持四人、三人日麻。
- 一局规则可以组合配置，并提供命名预设。
- 领域核心不依赖网络、数据库和具体客户端。
- 新增川麻、武汉麻将等玩法时，不修改日麻内部实现。
- 服务端对游戏状态拥有唯一写权限，客户端只提交意图。

## 分层

```text
Console / future GUI
        │ protocol
Server transport
        │ commands / events
Application services
        │ use cases
Domain core
        │ ports
Infrastructure
```

### Domain core

保存牌、玩家、房间、桌局、动作、事件和规则接口。该层只使用 Rust
标准库，保证规则计算易测试、可复用。

### Application

编排创建房间、加入房间、匹配、开始游戏和提交动作。事务、鉴权和并发
边界在这一层处理，不把网络对象传入领域层。

### Transport

HTTP 用于身份、房间和匹配等请求；WebSocket 用于桌局命令、事件和重连。
协议对象与领域对象分离，并带协议版本。

### Infrastructure

实现账号、房间快照、战绩、段位、事件发布等端口。初期使用内存实现，
之后可替换为 PostgreSQL、Redis 等，不影响领域规则。

## 核心扩展点

`RuleEngine` 是麻将玩法边界，负责：

- 玩家数量和牌集合；
- 规则配置校验；
- 合法动作生成与动作执行；
- 和牌、流局及计分；
- 连庄和对局结束判断。

日麻是该接口的一个实现。四人/三人的共享规则放在日麻模块中，人数差异
由经过校验的配置表达。其他麻将种类实现同一接口，不向日麻模块增加条件
分支。

规则预设只是不可变配置的工厂，不在计分代码中写诸如“如果是 ML 规则”
的分支。房间创建后保存完整规则快照和版本，避免预设更新影响进行中的牌局。

具体对象、聚合和不变量见 [对象模型](domain-model.md)。持久化格式见
[存储设计](persistence.md)，外部通信格式见 [通信协议](protocol.md)，
进程启动约定见 [后端运行骨架](server-runtime.md)，容器部署见

## 状态与并发

- 一个桌局同一时刻只由一个任务顺序处理命令。
- 每条客户端命令携带桌局版本，过期命令被拒绝。
- 领域对象执行命令后产生事件，再由外层持久化和广播。
- 随机种子在开局时生成并记录；测试可注入固定种子。
- 断线只改变连接状态，不直接改变牌局状态。

## 依赖规则

- `mahjong-core` 不依赖 `apps` 或基础设施。
- 领域层不执行 I/O、不读取时钟、不使用全局随机数。
- 网络 DTO 不作为领域实体使用。
- 跨层调用依赖接口，具体实现由进程入口组装。
