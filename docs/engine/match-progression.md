# 对局推进与前后端同步

状态：实现完成  
最后更新：2026-08-06

本文是牌局推进的权威定义。规则引擎、应用层、传输层和网页端出现分歧时，以
本文为准；改动任何一侧都必须先改本文，再让两侧同时对齐。

## 原则

- 唯一真相在服务端。前端只播放服务端给出的状态，不自行推导下一局是谁坐庄、
  对局是否结束。
- 服务端不知道动画长什么样，但知道动画要播多久。凡是玩家在动画播完之前看不见
  的局面，都不能开始扣他的思考时间。
- 前端播放的每一段动画都有明确上界，服务端的兜底时限严格大于这个上界。任何
  一段动画都不会被服务端从中间切断。
- 时间不进入事件日志。回放只依赖事件顺序，不依赖真实时钟。

## 一、名词

| 名词 | 字段 | 含义 |
|---|---|---|
| 一场对局 | `match` | 从开局到出结果的整体，包含若干局 |
| 一局 | `hand` | 从发牌到结算的一盘牌，`hand_index` 从 0 开始 |
| 场风 | `progress.round_wind` | 东、南、西、北 |
| 局数 | `progress.round_number` | 1 到人数，三麻最大 3，四麻最大 4 |
| 本场 | `progress.honba` | 连庄与流局累积的本场棒 |
| 立直棒 | `progress.riichi_sticks` | 桌面上尚未被领走的供托 |
| 亲家 | `progress.dealer` | 当前庄家座位 |

`hand_index` 是这场对局已经打过的局数，与 `round_number` 无关：连庄时
`hand_index` 增加而 `round_number` 不变。

## 二、单局内的阶段

单局状态机由 `mahjong-riichi` 的 `HandPhase` 定义，应用层据此决定谁上钟：

| 阶段 | 含义 | 上钟的座位 |
|---|---|---|
| `AwaitingTurnAction { seat }` | 该家摸牌后可以打牌、暗杠、加杠、自摸、九种九牌 | 该座位 |
| `AwaitingDiscard { seat }` | 该家副露后必须打牌 | 该座位 |
| `AwaitingResponses` | 有人打牌或加杠，等其他家吃碰杠荣 | 尚未应答且有合法响应的座位 |
| `Ended` | 本局已结束，等结算确认 | 无 |

一局之外还有两个不属于 `HandPhase` 的同步阶段，二者都不上钟：

- **开局准备**：发牌事件已经产生，但客户端还在播骰子和发牌动画。所有座位
  提交 `riichi.ready_for_hand { hand_index }` 之后才开始读秒。
- **本局结算**：`Ended` 之后服务端保留一份 `hand_settlement`。它分两段：各家
  先提交 `riichi.settlement_played { hand_index }` 报告结算动画播完，服务端
  据此开确认窗口并起算五秒倒计时；客户端这时才显示确认按钮，点了发
  `riichi.confirm_settlement { hand_index }`。全部确认或倒计时走完才开下一局。

这三个命令都带 `hand_index` 而不带 `expected_version`：它们是幂等的确认，
不能因为别人先确认导致版本号变化而失败。`hand_index` 不匹配时直接拒绝，
避免上一局的确认把下一局推掉。

## 三、一局结束后的推进

一局结算由 `HandSettlement::settle` 产出 `HandResult`，其中
`next_progress` 是下一局的进程。判定顺序如下。

### 3.1 连庄

| 结束方式 | 连庄条件 |
|---|---|
| 自摸 | 和牌者是亲家 |
| 荣和 | 和牌者之一是亲家（多家荣和只要有一家是亲家） |
| 荒牌流局，无流局满贯 | `dealer_continuation == win_or_tenpai` 且亲家听牌 |
| 荒牌流局，有流局满贯 | 流局满贯达成者之一是亲家，与 `dealer_continuation` 无关 |
| 途中流局（九种九牌、四风连打、四杠散了、四家立直） | 一律连庄 |

`dealer_continuation == win_only` 时，亲家听牌流局也要下庄。

### 3.2 本场

- 连庄：本场加一。
- 不连庄且本局有人和牌：本场归零。
- 不连庄且本局是流局：本场加一（流局的本场跨庄累积）。

### 3.3 立直棒

本局有人和牌或达成流局满贯时，桌上全部立直棒归给和牌者（多家荣和归给
最靠近放铳者的一家），`riichi_sticks` 清零；否则原样留到下一局。

### 3.4 亲家轮转与场风推进

不连庄时亲家按座位号加一取模；同时：

- `round_number < 人数`：局数加一，场风不变；
- `round_number == 人数`：场风推进一位（东→南→西→北），局数回到 1。

三麻的一个场风是三局，四麻是四局。

## 四、对局结束条件

一局应用到 `RiichiMatch::apply_hand` 之后，按以下顺序判定，**先命中先生效**。
`progress` 指刚打完这一局的进程，`points_after` 指本局结算后的点数。

1. **击飞**：`tobi` 开启且任何一家点数小于 0 → `Tobi`。
2. **已进入延长场**（`round_wind` 已经超过预定终局场风）：
   有人达到一位必要点数，或者本局已经是延长场的最后一局 → `ScheduledEnd`；
   否则继续。
3. **还没打到预定最终局** → 不结束。
4. **正在打预定最终局**：
   - `agari_yame` 开启、有人达标、亲家和牌连庄且亲家是第一名 → `AgariYame`；
   - 亲家不连庄且有人达标 → `ScheduledEnd`；
   - 其余情况继续（亲家连庄就继续打本局，亲家下庄就进入延长场）。

预定终局场风：东风战是东场，东南战是南场。因此

- 东风战打到东场最后一局，无人达到一位必要点数 → **南入**；
- 东南战打到南场最后一局，无人达到一位必要点数 → **西入**。

延长场是突然死亡：任何一局结束后有人达标就立刻结束，不看连庄，也不看
`agari_yame`。延长场打满一整个场风仍无人达标，也在该场风最后一局结束
（东风战最迟南 3／南 4，东南战最迟西 3／西 4）。

一位必要点数默认 30000，可以在房间规则里覆盖。想要「东风战固定打满 N 局」
的房间，把 `first_place_required_points` 设成起始点数（默认 25000）即可：
所有人开局就达标，永远不会进入延长场。

达标判定用的是各家手上的点数，**不含桌面上未被领走的立直棒**。供托在对局
结束后才按最终顺位归给第一名，只影响最终点数，不影响是否结束。

顺位在同分时按起家顺序（起庄座位起算的座次）决定，与真实时间无关，回放
可复现。

### 例：三麻东风战，全程无人和牌

三家全部摸切，每局都是无人听牌的荒牌流局，点数一直是 25000。

| hand_index | 场风局数 | 本场 | 亲家 | 判定 |
|---|---|---|---|---|
| 0 | 东 1 | 0 | 0 | 未到最终局，继续 |
| 1 | 东 2 | 1 | 1 | 未到最终局，继续 |
| 2 | 东 3 | 2 | 2 | 最终局；无人达到 30000 → 南入 |
| 3 | 南 1 | 3 | 0 | 延长场；未达标且不是最后一局，继续 |
| 4 | 南 2 | 4 | 1 | 同上 |
| 5 | 南 3 | 5 | 2 | 延长场最后一局 → `ScheduledEnd` |

同一张桌子若把 `first_place_required_points` 设为 25000，则在
`hand_index == 2` 结束，共 3 局。

## 五、时间与动画的同步契约

### 5.1 时钟归属

时间只有一个来源：服务端进程启动时刻。应用层只接收 `now_ms`，从不读时钟。
两段式思考时间的模型见[操作时限与断线](../protocol/turn-timer.md)。

### 5.2 上钟推迟到动画播完

一步操作产生的事件推送出去之后，客户端还要播一段动画；动画播完之前，下一个
决策者根本看不见他要应对的局面。因此服务端把新上钟的座位按
`now_ms + grace_ms` 上弦，`grace_ms` 是这一步操作的动画时长：

| 操作 | 动画 | 宽限 |
|---|---|---|
| 打牌 | 牌飞到牌河 | `DISCARD_FLIGHT_MS + ACTION_SETTLE_PADDING_MS` |
| 立直宣言打牌 | 横幅与飞牌同时播，取长 | `max(CALL_BANNER_MS, DISCARD_FLIGHT_MS) + ACTION_SETTLE_PADDING_MS` |
| 吃、碰、明杠、暗杠 | 横幅与推牌同时播，取长 | `max(CALL_BANNER_MS, MELD_PUSH_MS) + ACTION_SETTLE_PADDING_MS` |
| 加杠 | 只有横幅，牌直接叠在已有的碰上 | `CALL_BANNER_MS + ACTION_SETTLE_PADDING_MS` |
| 过、自摸、荣和、九种九牌、准备、确认、退出投票 | 无，或走结算流程 | 0 |

规则：

- 宽限只给**新上钟**的座位。已经在读秒的座位保留原 `armed_at_ms`，不会因为
  别人的动作回血。
- 上弦时刻可以在未来：`deadline_ms` 跟着后移，动画期间 `expired()` 为假，
  在动画期间就作答的座位一点长考都不扣。
- 超时动作走与玩家命令相同的 `execute` 路径，因此超时打出的牌同样享有宽限。
- 传输层把尚未流逝的那段宽限折进 `remaining_ms` 和 `base_ms`，客户端本地
  插值出来的秒数与服务端一致（见 `apps/server/src/clock.rs`）。
- 退出投票暂停时钟时，动画期间的剩余等待记为负数保存，恢复后继续等完。

### 5.3 开局准备

开局的牌还在往各家手上飞的时候，谁都还没看清自己的牌。这段时间服务端
**拒绝一切对局命令**（`InvalidGameCommand`），也不给任何座位上钟，直到这一局
的开局握手结束。握手用 `riichi.ready_for_hand { hand_index }`，幂等、不校验
版本号，客户端播完自己的开局动画就发一次。

放行时刻取下面两者中先到的一个：

| 情形 | 放行时刻 |
|---|---|
| 全部座位都报告了 | 最后一家报告的那一刻 |
| 至少一家报告了 | `第一家报告时刻 + ANIMATION_REPORT_GRACE_MS`（3 s） |
| 一家都没报告 | `发牌时刻 + OPENING_READY_FALLBACK_MS`（20 s） |

为什么可以只等一段固定的宽限：各家的开局动画是同一个发牌事件触发的，同时
起播、时长相同（骰子 2000 ms + 发牌 `openingDealDuration(人数)`，四麻约
4.3 s、三麻约 3.8 s），所以只要有一家播完，其他家要么马上就到，要么是被
浏览器挂到后台节流了——那种页面等下去也没有意义。一家都没报告说明这桌上
根本没有会走这个握手的客户端（例如控制台客户端），走那个长的兜底。

宽限到期后的放行由 `release_opening_if_due` 完成，它会推进版本并广播，因为
客户端在看到「全场都播完了」之前一直按着不让点牌，服务端不出声它就一直等。

客户端对应的判断：本地动画播完只是提交握手，真正解锁点牌要等视图里的
`opening_ready_seats` 集满（或中途进来的人看到牌局已经动过）。

### 5.4 本局结算

本局结束后服务端挂起 `hand_settlement`。结算分两段：客户端先自己把动画播完，
播完了报告一声；确认窗口和那五秒倒计时由服务端统一开、统一读。这样各家的
按钮什么时候出现、还剩几秒，全是同一个数，不会有人已经能点、有人还在看动画。

**第一段：客户端播放（各家本地计时）**

| 阶段 | 时长 | 说明 |
|---|---|---|
| 摊牌与役种 | 至多 `SETTLEMENT_REVEAL_BUDGET_MS` | 和了摊手、翻役种；流局逐家摊牌标听牌 |
| 结算读秒 | `SETTLEMENT_COUNTDOWN_MS` | 自动进入点数动画前的读秒 |
| 点数动画 | `POINTS_REVEAL_MS` | 点棒增减滚动 |

这一段完全由视图数据决定，各家同时起播、时长相同，正常只差网络抖动。面板上
那个按钮是本地的跳过键（多位和牌时先翻「下一位」，最后一位跳到点数动画），
按不按都不影响服务端。点棒滚完客户端提交 `riichi.settlement_played`。

**第二段：服务端确认窗口**

窗口开启时刻取下面三者中先到的一个：

| 情形 | 开窗时刻 |
|---|---|
| 全部座位都报告播完了 | 最后一家报告的那一刻 |
| 至少一家报告了 | `第一家报告时刻 + ANIMATION_REPORT_GRACE_MS`（3 s） |
| 一家都没报告 | `结算挂起时刻 + settlement_reveal_fallback_ms(番种条数)` |

开窗时把没报告的座位一并记成已播完，并把截止时刻 `开窗时刻 +
SETTLEMENT_CONFIRM_MS` 写进视图（`confirm_remaining_ms` 是它相对本次请求的
剩余毫秒）。窗口没开之前 `riichi.confirm_settlement` 一律被拒
（`InvalidGameCommand`），倒计时因此是权威的。

下一局开始的时刻取下面两者中先到的一个：全部座位都确认了，或者倒计时走完。
倒计时走完服务端自己开下一局，不必等谁点。

服务端的两个兜底时限按番种条数动态计算：番种越多前端逐条播报的时间越长，
兜底也因此给得更宽。没有番种时（荒牌流局）走下界保底。

```text
settlement_reveal_fallback_ms(yaku_count) = max(番种条数 * PER_YAKU_REVEAL_MS,
                                                 SETTLEMENT_REVEAL_FLOOR_MS)
                                           + SETTLEMENT_COUNTDOWN_MS
                                           + POINTS_REVEAL_MS
                                           + SETTLEMENT_FALLBACK_MARGIN_MS

settlement_fallback_ms(yaku_count) = settlement_reveal_fallback_ms(yaku_count)
                                    + SETTLEMENT_CONFIRM_MS
```

因此「服务端强制开窗」严格晚于「客户端自己播完并上报」，役种再多也不会被从
中间切断。客户端的摊牌阶段按 `SETTLEMENT_REVEAL_BUDGET_MS` 截断，这个上界
是硬的。

开窗和开下一局都必须走 `expire_clocks` 广播出去（`open_settlement_confirm_if_due`
和 `advance_settlement_if_due`）：客户端在收到新版本之前不显示确认按钮，
服务端不出声它就一直等。

客户端对应的规则：

- 确认按钮只在 `confirm_remaining_ms != null` 时出现，读的秒就是这个值，
  本地不另起倒计时、也不自动确认；
- 看到窗口开了但自己还卡在摊牌阶段（说明自己是被宽限补上的那家），直接跳到
  点数动画，免得倒计时都走完了还没看见按钮。

### 5.5 常量对照表

两份表必须逐字对应，改一处必须同时改另一处：

```text
crates/mamahjong-application/src/presentation.rs
apps/game-web/src/game/animationTiming.ts
```

| 常量 | 值 | 含义 |
|---|---|---|
| `CALL_BANNER_MS` | 1300 | 吃碰杠立直横幅从弹出到淡出 |
| `MELD_PUSH_MS` | 320 | 副露从手牌边缘推到副露位 |
| `DISCARD_FLIGHT_MS` | 460 | 打出的牌飞到牌河 |
| `ACTION_SETTLE_PADDING_MS` | 120 | 动画收尾到下家开始读秒的留白 |
| `SETTLEMENT_REVEAL_BUDGET_MS` | 12000 | 结算摊牌阶段的硬上界 |
| `SETTLEMENT_COUNTDOWN_MS` | 5000 | 结算面板自动推进读秒 |
| `POINTS_REVEAL_MS` | 2400 | 点数动画时长 |
| `SETTLEMENT_CONFIRM_MS` | 5000 | 服务端确认窗口的倒计时 |
| `SETTLEMENT_FALLBACK_MARGIN_MS` | 3000 | 服务端兜底相对客户端上界的余量 |

服务端专有、客户端不需要知道的时限：

| 常量 | 值 | 位置 |
|---|---|---|
| `ANIMATION_REPORT_GRACE_MS` | 3000 | `presentation.rs`，第一家报告动画播完后再等其他家的宽限（开局握手与结算握手共用） |
| `OPENING_READY_FALLBACK_MS` | 20000 | `presentation.rs`，全员未确认开局时的兜底 |
| `EXIT_VOTE_DURATION_MS` | 15000 | `game.rs`，退出投票时限 |
| `BASE_THINKING_MS` | 5000 | `clock.rs`，每次决策恢复的基础时间 |
| `RESERVE_THINKING_MS` | 20000 | `clock.rs`，每局补满的长考池 |

## 六、测试清单

规则引擎（`crates/mahjong-riichi`）：

- 各种结束方式下的连庄、本场、立直棒、亲家轮转；
- 东风战无人达标进入南场，东南战无人达标进入西场；
- 延长场有人达标立刻结束；
- 延长场打到最后一局无人达标也结束；
- 击飞先于预定终局；
- 和了止め只在全部条件同时成立时结束；
- 未领走的立直棒按最终顺位归给第一名，且不影响是否结束。

应用层（`crates/mamahjong-application`）：

- 打牌之后新上钟的座位 `armed_at_ms == 操作时刻 + 该操作的动画时长`；
- 动画期间 `expire_clocks` 不产出任何到期；
- 超时打牌与手动打牌给出相同的宽限；
- 开局未全部确认时无人上钟，且任何对局命令都被拒绝；
- 第一家报告开局后过了宽限，服务端替其余座位补上并放行；
- 确认窗口未开时 `riichi.confirm_settlement` 被拒；
- 第一家报告结算动画播完后过了宽限，服务端替其余座位开窗，各家读到同一个截止时刻；
- 确认倒计时走完，无人点确认也自动开下一局；
- 结算兜底严格晚于客户端播放上界。

传输层与端到端（`apps/server`）：

- 一场完整的三麻东风战能通过公开 HTTP 接口打完，局数与规则一致；
- `remaining_ms` 含未流逝的动画宽限，重连后连续。
